# ADR 0001：聊天文件夹命名时序——日期文件夹为工作区 + slug 子文件夹

- 状态：已接受
- 日期：2026-08-13
- 修订：2026-10-07（见文末「修订」，决策本身未变）

## 背景

需求要求聊天区会话在 `Documents/DSH/年-月-日/xxxx/` 下拥有专属文件夹作为文件工作区，其中 `xxxx` 按用户第一句话由 LLM 生成简短的英文描述。

## 约束

DSH 会话的工作目录（cwd）在**创建会话那一刻**写入会话头部并永久冻结，之后无法修改（头部验证、恢复时的 `SessionCwdConflict` 检查、工作区账目按 cwd 归集都依赖它）。而"新会话"按钮必须立即创建会话（空白会话），此时第一句话尚不存在，`xxxx` 无从得知。

尝试过的替代方案：

- 先建临时名文件夹冻结 cwd、第一句话后再改名/搬迁 → 会话头部 cwd 与工作区记录 path 均无法跟随，重启后会话被账目过滤成"游离"。
- 先无 cwd 创建会话、第一句话后补建 → cwd 冻结后无法补写。
- 拦截 composer 首条消息、先建文件夹再创建会话 → 需要深度侵入会话创建流程，脆弱。

## 决策

采用两段式：

1. 点"新会话"立即创建会话，cwd 冻结为 `Documents/DSH/YYYY-MM-DD/`（日期文件夹，每天一个，在侧边栏"工作区"区域隐藏）。
2. 第一句话发出后，宿主端用 LLM 生成 2–4 个英文小写单词的 slug（失败回退本地规则），创建 `Documents/DSH/YYYY-MM-DD/xxxx/` 子文件夹并写入 `.dsh-chat.json` 标记；通过系统提示让 agent 把该会话的文件读写默认放在该子文件夹。

## 后果

- 优点：文件夹命名完全满足"按第一句话生成英文描述"；会话创建流程零侵入；每聊一个文件夹、可读可写、防冲突（重名自动加 `-2`）。
- 代价：DSH 意义上的"工作区"是日期文件夹而非 `xxxx` 子文件夹，agent 工具默认 cwd 是日期文件夹（由系统提示补偿引导）；已归档会话列表暂时以会话时间而非归档时间展示（归档集合是纯 id 数组，无时间戳）。
- 聊天文件夹归属关系由文件夹内的 `.dsh-chat.json` 标记自描述，重启后扫描重建，无额外中心化存储。

## 修订

2026-10-07。决策 1、2 本身不变（会话创建时冻结日期文件夹 cwd；slug 子文件夹仍在第一句话之后由 LLM 命名）。本轮明确了两件当时没写、后来靠实测才逼出来的事：

1. **告诉 agent 用哪个文件夹的那一节，置位要早于落盘。** 第一节必须在该会话**第一句话投递到 agent** 时就进入提示词，而不是等那条消息落进会话日志。DSH 的 agent loop 是"先组装提示词 → 提交 `system/message` → 才 append 被认领的 `user/message`"，所以挂在 append 上的置位对它自己那一步恒为时已晚：模型第一步会把文件写进日期文件夹，等**下一步**的提示词点名聊天文件夹才去搬。文件夹本身仍按决策 2 在第一句话之后创建；提前的只是"先别乱写、先看看"这个窗口——**这不是对决策的修改，而是决策 2 里"通过系统提示让 agent 把文件读写放在子文件夹"要真正生效的前提**。
2. **被委派的子会话不建自己的聊天文件夹。** 子会话继承父会话的 cwd，其任务消息又是 `source: { kind: 'user' }`，因此命中一切"这是聊天会话"的判据；按本 ADR 的字面实现会给每个子会话建一个按任务命名的文件夹。现在子会话（`SessionHeader.origin === 'subagent'`）不建文件夹，并按 `SessionHeader.parentSession` **一跳**指向委派它的那个聊天的文件夹（查不到就不给指引）。**"聊天文件夹"是聊天的容器，不是子会话的容器**——这条是对决策 2 的补充边界，值得记下来是因为它不可能从"按第一句话命名"推出来。
3. **`.dsh-chat.json` 是共享文件，写入必须读-改-写、原子替换；认领文件夹名必须与创建同一步。** Web 与桌面端是**两个 profile、两个宿主进程**，却共用同一个聊天根（见 AGENTS.md「Web UI 与桌面端共用同一份代码」），而每个进程只知道**自己启动之后**登记的条目——按"本进程内存里的登记表"整份重写该文件，会抹掉另一个宿主刚写的条目，而被抹掉登记的文件夹随即落进"无人认领 = 可收养"的规则里，两个聊天就可能共用一个文件夹。所以写入只改调用方点名的那一条，并且**先写同目录临时文件再 `rename` 覆盖**（否则另一个宿主可能读到一个写了一半的文件、把它当成空登记表，再把自家条目写进去——那正是"抹掉对方条目"的另一条路径）；读到的文件戳（size+mtime）在替换前再比一次，变了就重做读-改-写，最多三次。同理，`uniqueSlug` 过去是"先 `existsSync` 看名字空不空、再在别处 `mkdir`"，两步之间隔着 slug 生成的整个 `await`，两个同时开聊的会话有真实概率选中同一个名字；现在改成**在同一同步步骤里 `mkdirSync` 认领**（非 `recursive`，靠 `EEXIST` 认输并试下一个候选）。收养规则也跟着收紧了：**只有本次命名开始时就已存在**的同名目录才算"无人认领的孤儿"、可以被收养；搜索过程中**新出现**的目录是别的宿主（或本宿主片刻之前）刚认领下来的，一律让路（`mkdirSync` 会以 `EEXIST` 把它推到下一个候选）——否则"看一眼 `existsSync` 就收养"会把对方刚建好的文件夹直接抢过来，两个聊天照样共用一个文件夹。三条都是决策 2 里"防冲突"与"自描述、扫描重建"落地时才会暴露的实现级不变量。
